## 一、正式引入 `TrackPointTool`

### 1. 新增 Potree 内部轨迹点工具

新增 `[src/utils/TrackPointTool.js](D:/code2/potree/src/utils/TrackPointTool.js:1)`，这是本轮 Potree 工作区最核心的新增能力。

它承担了以下职责：

- 持有 Potree 内部的轨迹点数据和展示状态。
- 根据 `size / opacity / range / activeIndex / showLabel` 构建圆环 mesh。
- 在 Potree 内部执行 hover 和 click 拾取。
- 通过 `track_point_click` 事件把点击结果抛给宿主层。
- 在工具内部处理 mesh 与 sprite 的释放，不再让业务项目直接接触 Potree 内部对象。

这意味着轨迹点圆环的渲染责任正式落在 Potree 内部，而不是继续由外层 React 项目创建 mesh 后再塞回 Potree。

### 2. `TrackPointTool` 当前的渲染方式

`TrackPointTool` 当前不是把圆环挂到 `viewer.scene.scene`，而是维护了自己的独立场景：

- `this.scene = new THREE.Scene()`：[TrackPointTool.js](D:/code2/potree/src/utils/TrackPointTool.js:224)
- `this.group` 挂在这个独立 scene 下：[TrackPointTool.js](D:/code2/potree/src/utils/TrackPointTool.js:226)
- 监听 `render.pass.perspective_overlay`：[TrackPointTool.js](D:/code2/potree/src/utils/TrackPointTool.js:240)
- 在 overlay pass 里单独渲染自身 scene：[TrackPointTool.js](D:/code2/potree/src/utils/TrackPointTool.js:545)

这样设计的直接目的是避免轨迹点圆环被 EDL 点云的全屏合成结果覆盖。

### 3. 为什么要改成 overlay 渲染

此前如果圆环挂在 `viewer.scene.scene`：

- 普通 Potree 渲染时通常还可以依赖 `depthTest: false` 和较高 `renderOrder` 顶在点云上方。
- 但在 `EDLRenderer` 下，主场景会先绘制，然后再做 EDL 全屏合成，之前画出来的圆环会被后续的屏幕空间结果盖住。

因此，本轮 `TrackPointTool` 的重要设计结论是：

- 如果轨迹点圆环需要像测量标记一样“无论点云是否开启 EDL 都不会被遮挡”，就必须使用独立 overlay scene，而不是继续放在主场景里。

## 三、TreeTagTool 对点云效果默认值的处理调整

`[src/utils/TreeTagTool.js](D:/code2/potree/src/utils/TreeTagTool.js:411)` 中有一处关键改动：

- 旧逻辑：在非多点云模式或没有 tag 时，对点云执行 `clearPointcloudEffects(pc)`。
- 当前逻辑：改为执行 `this.viewer.applyPointcloudEffectDefaults(pc)`：[TreeTagTool.js](D:/code2/potree/src/utils/TreeTagTool.js:414)

这个改动的目的不是新增效果，而是防止 TreeTagTool 在不相关场景里把当前点云的默认效果状态清回普通模式。

它直接服务于业务项目当前的需求：

- 主场景点云和实景点云都要能跟随全局 `EDL / XRAY / 普通` 状态。
- Potree 内部的 TreeTag 逻辑不应该再在点云切换时偷偷把效果状态抹掉。

## 四、controls 兼容层的相关改动

当前 Potree 工作区里还有一组与本轮联调关系密切的控制器兼容改动，这些改动虽然不属于轨迹点工具本身，但会直接影响主场景点云、实景点云和实景漫游之间的控制器切换。

### 1. `camera-controls` dist 增加 `setCamera`

`[libs/camera-controls/dist/camera-controls.module.js](D:/code2/potree/libs/camera-controls/dist/camera-controls.module.js:1419)` 当前工作区增加了：

- `camera` setter 内的相机切换保护。
- `zoom` 同步。
- 默认滚轮与双指语义的按相机类型刷新。
- 新的 `setCamera(camera)` 方法。
- `setScene(scene)` 改为走 `setCamera(scene.getActiveCamera())`。

这组改动的目标是让旧 `cameraControls` 在透视 / 正交相机切换后，仍能挂到当前 active camera 上，不至于继续绑着旧相机实例。

### 2. `viewer.js` 在投影切换后同步 controls 上下文

`[src/viewer/viewer.js](D:/code2/potree/src/viewer/viewer.js:1344)` 附近额外补了：

- `setCameraMode` 切换投影后，立即对当前 `controls` 执行 `syncControlsContext(...)`。
- 如果存在旧 `cameraControls` 且它不是当前活动 controls，也同步一次上下文。
- 将旧 `cameraControls` 的能力声明从 `supportsSetCamera: false` 改成 `supportsSetCamera: true`。[viewer.js](D:/code2/potree/src/viewer/viewer.js:1570)

这组逻辑是为了解决旧 `cameraControls` 在正交模式、实景点云模式和宿主侧相机桥接时的上下文错位问题。

## 六、当前 Potree 工作区的整体定位

从本次改动结果看，`D:\code2\potree` 工作区已经不只是“给业务项目打补丁”，而是在朝以下方向演进：

1. 将业务项目原本注入 Potree 的临时渲染能力，收回为 Potree 内部正式工具。
2. 通过 `Viewer API` 承接宿主数据，而不是直接耦合宿主 store。
3. 逐步修正旧 `cameraControls` 与当前 active camera、正交投影、宿主桥接之间的兼容关系。
4. 避免 Potree 内部工具在无关场景中误改点云效果默认值。

## 七、后续整理提交时的建议拆分

若后续需要把 Potree 工作区整理成更清晰的提交，建议至少拆成两组：

1. `TrackPointTool + Viewer API + overlay 渲染`
2. `camera-controls / viewer controls 上下文兼容 + TreeTagTool 效果默认值修正`

这样可以避免“轨迹点工具迁移”和“控制器兼容修复”混成一个难以回溯的大提交。
